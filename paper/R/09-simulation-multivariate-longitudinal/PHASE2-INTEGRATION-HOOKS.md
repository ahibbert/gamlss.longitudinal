# Phase 2 central integration hooks

This file records integration changes for the central replication controls. It
does not apply them. Apply these hooks only after the 100-replicate Phase 2
audit reports no failures.

## `paper/_targets.R`

Module 07 already calls `jss_run_07_from_public_results(settings)` for the paper
profile and `jss_run_07_gamma_copula_misspecification()` for the full profile.
Both producers now return the selection-attempt data and the confusion and
failure tables, so no new Module 07 target is required.

For Phase 2 benchmark evidence, source
`paper/R/09-simulation-multivariate-longitudinal/00-multivariate-setup.R` and add
a file-producing target after the production checkpoint directory has been
independently approved. Central integration must call
`mvt_integrate_approved_phase2_snapshot(run_dir, destination_dir)`; direct CSV
copying is not an eligible route. The function validates the external approval,
copies the immutable snapshot/checkpoints and exact evidence allowlist through a
fresh staging directory, revalidates before and after atomic installation, and
returns the approved snapshot identity. Claim producers must call
`mvt_validate_phase2_claim_evidence()` before resolving claim rows.

The exact public allowlist is generated by
`mvt_phase2_public_output_allowlist()`. It contains the following attempt and
provenance artifacts; no exploratory checkpoint, sensitivity, or summary file
outside this list is eligible for central integration:

- `scenario_grid.csv`
- `run_metadata.csv`
- `package_versions.csv`
- `worker_attestations.csv`
- `checkpoint_rejections.csv`
- `fit_status_by_rep.csv`
- `benchmark_results_by_rep.csv`
- `coefficient_results_by_rep.csv`
- `dependence_recovery_by_rep.csv`
- `variogram_scores_by_rep.csv`
- `runtime_by_rep.csv`

The evidence-artifact portion of that same allowlist is:

- `gee_family_results.csv`
- `gee_unstructured_stress_test.csv`
- `nearest_neighbor_results.csv`
- `nearest_neighbor_paired_contrasts.csv`
- `capability_snapshot_2026-09-01.csv`
- `comparator_scope_registry.csv`
- `phase2_attempt_reconciliation.csv`
- `phase2_benchmark_audit.csv`
- `phase2_benchmark_audit.md`

The producer accepts only a committed immutable `aggregate_snapshot.rds` whose
checkpoint manifest and aggregate hashes still reconcile. Claim-facing hooks
must additionally pass `mvt_validate_phase2_claim_outputs()` and supply exact
scenario/row keys, metric, direction, denominator, effect artifact/column,
MCSE column, and confidence-interval columns. Count-only claim bindings are not
sufficient.

The full profile can write a candidate record only after the exact 1,600-case,
14,400-row snapshot passes every one of the 28 registered audit checks. A
one-case/nonproduction run cannot emit a candidate. The candidate is written outside the mutable run
directory under the module-level `snapshot-candidates/` directory. Publication
and paper-profile consumers must require a checkout-external detached Ed25519
attestation and signature created with the pinned Phase 2 production key. The
signed payload binds the root snapshot SHA-256, exact configuration and
producer, artifact/checkpoint manifests, complete production audit, approver,
and approval time. Internal commit files, ownership records, mutable CSV
registries, or a self-updated root commit are not publication trust anchors.

Make the promoted Phase 2 target a dependency of `public_outputs`; do not point
the central target graph at a mutable exploratory `results/` directory.

## Release gate

Do not cite, manifest as active, or copy tables from a run unless all of the
following reconcile:

- exactly the registered `t20` time grid, four-family, four-dependence,
  100-replicate design, yielding 1,600 unique scenario-grid cases;
- exactly nine planned methods and 14,400 fit-status plus 14,400 benchmark rows;
- every `phase2_benchmark_audit.csv` row has status `pass`;
- the downstream `review_audit.csv` has no failures;
- no full-vine sensitivity rows are present in the headline run directory.

Unfrozen exploratory or partial review directories are not capability evidence
and may not be used as publication-readiness inputs. Only the exact allowlisted
artifacts from a production-eligible run may be promoted.
